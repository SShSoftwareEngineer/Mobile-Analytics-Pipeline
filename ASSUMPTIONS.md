Так как исходные CSV-файлы не были предоставлены, был разработан скрипт генерации тестового датасета.

Для генерации тестовых данных использовалась библиотека Faker. В логику генерации были заложены вероятности появления 
описанных в ТЗ аномалий: повторные `event_id` с обновленной выручкой, задержки `ingested_at` относительно `event_time` на 
срок до нескольких дней, невалидные значения `country` ('--', пустые строки, нижний регистр), тестовый 
трафик (is_test = true), а также разделители в виде запятых и "NULL" в финансовых полях. Для ускорения работы при создании
скрипта использовался ИИ-инструмент Antigravity.

Надо учитывать возможность наличия некорректных данных в исходных файлах. 
Поэтому таблица events_raw рассматривается как промежуточный слой, и все столбцы из CSV-файлов загружаются как текстовые. 
Это позволит сохранить исходные значения и проверить/преобразовать их типы позже. 
По условиям задачи в денежных типах данных разделитель запятая, а не точка.
В остальных таблицах по условиям задания нет некорректных данных, поэтому дополнительные усложнения не вводятся.

Строка считается невалидной для конкретной задачи, если значение поля отсутствует или некорректно, необходимого для выполнения этой задачи. 
В рамках задания реализуется обработка только тех некорректных случаев, которые явно указаны в задании. 
Для остальных случаев предполагается, что исходные значения корректны по умолчанию.

Поля `revenue_usd` и `country` обрабатываются по специальным правилам задания и сами по себе не являются причиной отправки строки в карантин.

### Задача 2.1 — Удаление дубликатов 

Если несколько записей имеют одинаковые `event_id` и `ingested_at` (что на практике маловероятно), выбор строки произойдет 
случайным образом. Необходимы дополнительные правила для выбора актуальной записи на основе бизнес-логики, чего нет в условиях задачи.

Для полей `event_time` и `ingested_at` предполагаем, что они содержат корректные значения даты и времени в текстовом формате.
Для поля is_test предполагаем, что оно содержит корректное значения true в текстовом формате, остальные значения по умолчанию false.

### Задача 2.4 — Инкрементная загрузка

Если поле `ingested_at` события содержит дату и время загрузки информации в систему, то оно обладает такими свойствами:
1. Поставщик события не управляет `ingested_at`.
2. Каждая новая поступившая запись события от любого поставщика получает текущее время записи в систему.
3. `ingested_at` в таблице фактов всегда только увеличивается с новыми данными.
4. Нам известно последнее значение `ingested_at` по таблице фактов.

### Задача 3.1 — Очистка

Для этого задания выбрана построчная обработка записей в исходном Dataframe. Для больших объёмов данных векторизованные 
операции pandas/polars эффективнее, однако в рамках задания входной набор данных небольшой, а последующие запуски 
предполагают обработку небольших инкрементальных добавок. Поэтому приоритет отдан понятности кода, прозрачности 
обработки, возможности отдельно валидировать каждую строку, формировать `invalid_fields` и помещать некорректные 
записи в quarantine, используя `itertuples()`. При масштабировании такой подход потребовал бы пересмотра в пользу 
векторизованной обработки или потокового/пакетного подхода.  
Временные метки `event_time` и `ingested_at` в исходных данных считаются представленными в UTC, как указано в задании. 
В Python они преобразуются в timezone-aware datetime с часовым поясом UTC без изменения значения времени.  
Денежные значения `revenue_usd` обрабатываются как `Decimal` с точностью до двух знаков после запятой вместо 
Python float, чтобы избежать ошибок двоичного представления денежных значений. Пустые значения, NULL и значения, 
которые невозможно преобразовать в число, преобразуются в Decimal("0.00") и отдельно учитываются в статистике. 
Значение `country` считается корректным, если после удаления пробелов оно содержит ровно две буквы. Значение приводится 
к верхнему регистру. Пустые, `--` и другие значения, не соответствующие этому формату, преобразуются в `XX`, как 
предусмотрено заданием.  
Строка данных считается невалидной, если после нормализации содержит пустое или некорректное значение поля, 
необходимого для дальнейшей обработки. В рамках задания такими полями считаются `event_id`, `app_id`, `event_time` и 
`ingested_at`. Некорректные значения `revenue_usd` и `country` не делают строку невалидной, поскольку для них заданы правила
нормализации. Невалидные строки не удаляются, а помещаются в отдельный quarantine с перечнем проблемных полей в `invalid_fields`.
Для `user_id`, `event_name`, `media_source` и `campaign` отдельные правила валидации не вводятся, поскольку задание не 
определяет допустимый набор значений для этих полей. Предполагается, что их значения корректны.  
Записи с is_test = true считаются валидными данными, но исключаются из дальнейшей обработки и не попадают в 
clean_df, поскольку по условию задания тестовый трафик не должен входить в отчёты. Такие строки учитываются отдельно 
в статистике.  
Значение после удаления пробелов и приведения к нижнему регистру считается тестовым только при равенстве "true". 
Остальные значения рассматриваются как false.  
Для одинакового `event_id` сохраняется запись с максимальным `ingested_at`. Количество удалённых строк дубликатов 
учитывается в Counter как количество строк, не вошедших в итоговый набор после дедупликации. Если несколько записей 
имеют одинаковые `event_id` и `ingested_at`, дополнительный критерий выбора не вводится, поскольку такой критерий не 
определён условиями задания.

### Задача 3.2 — Небольшой конвейер

Для повторного запуска используется исходный events_raw.csv, поэтому результат перезаписывается, а не накапливается 
в результатах предыдущего запуска.
Выходной Parquet dataset и quarantine dataset формируются заново при каждом запуске.
В условиях задания указано, что скрипты должны находиться в python/, но пример запуска использует модуль pipeline.run. 
Поэтому скрипты размещены в python/pipeline/, а каталог python/ используется как source root.
