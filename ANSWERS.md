### Задача 2.2 — Оконные функции

SQL 1 — формирование `app_daily_revenue`:

Для каждого приложения и каждого календарного дня считается суммарная выручка по таблице фактов.
Начальная дата - дата запуска приложения, конечная - дата последнего события в наборе данных.
Сформируйте календарные записи: по одной строке для каждого приложения на каждый календарный день.
Добавьте данные о ежедневной выручке в полученный календарь; для дней, в которые не было событий, укажите нулевую выручку.

SQL 2 — формирование метрик

По таблице фактов формируется промежуточная таблица `app_daily_revenue` содержит в каждой строке `app_id`, дату и суммарную 
выручку daily_revenue за этот день, включая дни без событий (в этом случае daily_revenue = 0).
Это необходимо для корректного расчета скользящего среднего за 7 дней. Без строк с daily_revenue = 0 для пропущенных 
дней функция AVG() делила бы сумму на количество имеющихся строк, а не на количество календарных дней в окне. Также это
позволяет корректно посчитать скользящее среднее, когда с момента запуска приложения прошло менее 7 дней.

По таблице `app_daily_revenue` рассчитываются метрики:
- накопленная выручка с помощью оконной функции SUM().
- скользящее среднее за 7 дней с помощью функции AVG(), охватывающей текущий день и шесть предшествующих календарных 
дней или с момента запуска приложения, если прошло менее 7 дней.
- выручка за предыдущий день считается с помощью функции LAG(), потом определяется изменение выручки в процентах к 
предыдущему дню. Если предыдущий день отсутствует или выручка за него равна нулю, возвращается NULL.

### Задача 2.3 Revenue + Cost + ROAS

Ежедневную выручку для каждого `app_id`, media_source и campaign считаем по таблице фактов, используя функцию SUM().
Получаем требуемую таблицу с ежедневной выручкой, затратами и ROAS с помощью FULL OUTER JOIN с таблицей campaign_costs.
Такой тип соединения позволяет сохранить все строки из обеих таблиц, даже если для некоторых комбинаций `app_id`, 
media_source и campaign отсутствуют данные по ежедневной выручке или затратам и не дает дупликации строк. 
Соотношение выручки к затратам (ROAS) рассчитывается как отношение daily_revenue к daily_cost. Если 
daily_cost = 0, то ROAS = NULL.
Для решения проблемы деления на ноль можно использовать:
-	метод начислений (принцип соответствия доходов и расходов) из бухгалтерской практики. Вероятно, будет сложным в реализации в рамках данной задачи
-	вместо отношения брать разницу (revenue – cost)
Соотношение выручки к затратам (ROAS) позволяет оценить эффективность рекламных кампаний (campaign) в разрезе 
приложения (`app_id`) и площадки размещения (media_source). Чем выше ROAS, тем эффективнее рекламная кампания. 
Если ROAS < 1, то рекламная кампания убыточна.
Если daily_cost > 0 и daily_revenue = 0, это может быть долгосрочная рекламная кампания, которая принесет
увеличение продаж в будущем за счет повышения узнаваемости бренда, привлечения новых пользователей.
Если daily_cost = 0 и daily_revenue > 0, это возможно за счет предыдущих кампаний иил использования каких-то бесплатных ресурсов.
В обоих случаях такие аномалии могут сигнализировать об ошибках в учете.

### Задача 2.4 — Инкрементная загрузка

Для выбора новых данных фильтруем по `ingested_at`, так как это значение соответствует новым версиям событий, 
включая исправления, а `event_time` отражает момент возникновения события и не меняется при его повторной отправке.

Исходя из сделанных допущений фиксированное окно в днях для выбора новых событий не используется. В качестве нижней 
границы используется максимальное значение `ingested_at` из таблицы фактов, поэтому в обработку попадают все записи, 
поступившие после него, включая поздние события и исправления. После загрузки необходимо выполнить перерасчёт 
затронутых агрегатов и ежедневных отчетов за даты `event_time`, поскольку позднее поступившее событие может изменить 
уже рассчитанные исторические показатели задним числом.

### Задача 2.5 — Качество данных

После каждой загрузки целесообразно выполнять три проверки:

1. После предусмотренной в пайплайне дедупликации в events_fact не должно быть нескольких записей с одним `event_id`. 
Если такая ситуация обнаружена, конвейер останавливается, так как это указывает на ошибку в обработке данных 
и может привести к двойному учёту событий.
2. Проверка выявляет события, для которых `event_time` > `ingested_at`. При обнаружении таких записей конвейер  
останавливается, поскольку это нарушает ожидаемую последовательность времени события и нарушает логику конвейера.
3. Проверка выявляет записи, для которых `revenue_usd` < 0. При обнаружении таких записей выводится предупреждение,  
так как отрицательная выручка может быть из-за особенностей учета хозяйственных операций и не обязательно останавливать конвейер.

### Задача 3.1 — Очистка

Порядок очистки:
1. Проверяется весь events_raw.csv. Тестовые события (is_test = true) исключаются, поля `revenue_usd` и `country` 
нормализуются по заданным правилам.
2. Невалидные записи помещаются в quarantine. Невалидными считаются записи с пустыми или некорректными 
`event_id`, `app_id`, `event_time` и `ingested_at`. Создается поле с перечислением некорректных полей.
3. Для записей с одинаковым `event_id` оставляется запись с максимальным `ingested_at`. 
4. После этого применяется фильтр --since.
5. При обработке ведется подсчет статистики всех случаев
6. Результатом обработки events_raw.csv являются DataSet чистых и карантинных данных, а также статистика

### Задача 3.2 — Небольшой конвейер

1. читает events_raw.csv
2. Выполняет очистку и валидацию, помещая некорректные критические записи в карантин. 
3. Удаляет устаревшие копии событий по `event_id`.
4. Применяет фильтр --since. 
5. Записывает очищенные события в Parquet с разбиением по event_date, а невалидные события в quarantine.
6. В консоль выводится однострочная статистика обработки. 
Повторный запуск за тот же период не изменяет уже записанные данные: Parquet 
записывается в тот же dataset с теми же разделами по датам, а текущий результат формируется заново из исходного CSV.  
При ошибке в середине записи часть нового результата может остаться в выходном каталоге; для безопасной записи можно 
сначала записывать результаты во временный каталог, а после успешного завершения заменять им целевой каталог.

### Задача 3.3 — Чтение чужого кода 

1. При работе с внешними данными необходима проверка на соответствие типов и некорректные значения (TypeError, Null, NaN).
При конкатенации row["app_id"] + "-" + row["media_source"] код упадет с TypeError, если данные имеют числовой тип (int), 
или создаст невалидный ключ при наличии NaN/Null.
2. Падение на .astype(float): Преобразование упадет с ValueError, если в данных окажется нечисловое значение, пустая строка или Null.
3. Нет обработки FileNotFoundError для файла данных. Загрузка CSV целиком может вызывать OutOfMemory. Надо читать 
файл чанками (chunksize) и/или загружать только необходимые колонки (usecols).
4. С датами надо работать как с DateTime, а не как со строками. str.startswith(day) дает ложные срабатывания, зависит 
от строкового формата даты и падает при некорректном значении. С датами нужно работать через Timestamp (pd.to_datetime).
5. Отсутствие обработки пустого результата. Если фильтр не найдет совпадений, пустой датафрейм потеряет 
структуру/колонки и сломает дальнейшую обработку.
6. Нельзя использовать тип float для денег. float накапливает вычислительную погрешность округления. Для финансовых 
расчетов следует применять Decimal или int в минимальных денежных единицах.
7. Цикл iterrows() работает очень медленно из-за накладных расходов на создание Series и может искажать типы данных. 
Надо заменить на векторные операции (groupby) или itertuples().
8. Избыточные преобразования структур данных при сборке dict через промежуточные преобразования: 
→ list comprehension → DataFrame создает лишнюю нагрузку на память и процессор.

Написание кода с учетом всех замечаний и без дополнительной информации о задаче займет слишком много времени, 
поэтому я ограничился перечислением замечаний.
